# Backend
The backend implements the server, the Docker scanner and data storage. The server `app.py` is a separate process and handles requests from the UI. It needs to access the data. The Docker scanner `scanner.py` is a separate process and communicates with the Docker daemon to retrieve log messages from other Docker containers. It writes log messages to the database.

The data is split into three concerns: configurations, logs and records. Data access is implemented via data collection handlers under `/data`. These handlers are shared objects between the two processes. 





## Flask Server
This project uses *Flask*, a Python framework, to host the backend server and implement different endpoints (i.e. URL paths). The server handles two scopes of endpoints: pages requested via the browser and API endpoints requested by the frontend code.




### Single Page Application
This application is implemented as a single-page-application (=SPA), so it technically is only is a single HTML page, while it behaves likes multiple pages. Content is shown/hidden based on the state or user input. There is only one endpoint to serve *the* HTML page (`index`). It is served under the default path `/` or any other path not starting with `/api/`.

**Example:** If the user directly visits the *Settings* page via `/settings`, the request is still handled by the `index` endpoint and returns *the* HTML page. The code in *the* HTML page checks the current URL path and displays the content accordingly.




### API Endpoints
The other API endpoints start with the `/api/` prefix. The files are structured in the same way the paths are structured. The main path `/` is implemented in the `app.py` file. All `/api/` paths are implemented in the `api` folder. Endpoints that handle forms, are implemented under the `/api/form/` path in the `/api/form.py` file.

Exceptions that are raised within the API endpoints, get handled by the `error()` function in the `__init__.py` file. It uses a custom `my_traceback()` function to reduce the length of the error message. It returns a traceback that only includes frames whose file paths are within the specified project root directory. Frames deeply buried inside the *Flask* framework get ignored.





## Docker Scanner
All Docker containers on the host system (your machine) are handled by the Docker daemon. The daemon manages containers and provides an API via a socket. The scanner uses this API to retrieve log strings that were generated by a container.

The scanner is a separate Python program running parallel to the Flask server. It reads log messages from other Docker containers in a regular interval. The scanner uses a client that connects to the Docker daemon. 




### Docker Daemon Socket
The environment variable `DOCKER_HOST`, tells the client where to connect. The environment variable is set in the `Dockerfile`.

If the scanner runs directly on the host machine (e.g. during development), make sure to set the variable manually, with the path of the daemon socket on your machine.
Example: If you are running on **Linux** and use **Docker Desktop**, your variable could look something like this: `unix:///home/<user>/.docker/desktop/docker.sock` 




### Watchlist
By default the scanner considers logs from containers in the same Docker network. The user can set a network name to overwrite this behavior (or if the scanner is not part of any Docker network). The scanner then considers logs from containers in the given network. This can be helpful during development, while the scanner is not running inside a Docker container.

If the scanner is not part of any network and no network name is given, logs from containers on the entire host machine are considered. This is only a fallback mechanism and not recommended.

Users can use a whitelist and blacklist to additionally filter, the logs of which container are actually read. Both lists have container names or IDs. If the whitelist is empty, the logs of all running containers are read. Logs from containers in the blacklist are ignored. Changes are only effective after a restart of the scanner (i.e. the container).

Containers that pass through the whitelist and blacklist filters form the final watchlist. The application then reads the logs only for these specific containers.




### Similarity Matcher
Most logs are nice to have but are not much of interest. Some logs are of more interest, maybe those describing an error! It is possible to keep those logs and record them for later. The default way to record logs, is to enable auto-recording for a category (e.g. error). Any time a log has this category, the system checks if a matching record already exists. If a match is found, the system simply updates the existing record’s timestamp instead of creating a duplicate. For a log to match an existing record, they must share the same container, the same category, and similar message strings.



#### Weighted Jaccard Similarity
The scanner uses a *Similarity Matcher* to calculate a similarity score between two message strings. A fuzzy string matcher specifically designed to distinguish between the "skeleton" of a message (the human-readable parts) and the "variable" noise (IDs, paths, hex codes).

Each message string is split into tokens and each token gets a weight. This process is called vectorization. Tokens that are natural human words are most likely skeleton tokens and therefore considered more important. They get a higher weight. Tokens that are longer than 15 characters (likely no natural word), include numbers or include special characters are most likely variable tokens. They get a lower weight.

The *Weighted Jaccard Similarity* $J$ is defined by $J(A,B)=\frac{|A\cap B|}{|A\cup B|}$. The sets $A$ and $B$ are the vectorized token weights. This is a symmetric measure. If message A is "Error at /path/1" and message B is "Error at /path/2", the weighted Jaccard will be high because the heavy "Error" and "at" match, while the light paths mismatch. However, if message B is twice as long as message A, the score drops because the denominator (the union) grows much larger.



#### Containment
Containment is defined as $C(A, B) = \frac{|A \cap B|}{|A|}$. It essentially asks: "Regardless of how much extra junk is in message B, does it contain the important parts of message A?" If A is "Service started" and B is "Service started on port 8080 at 12:00 PM", the containment score will be very heigh, because all of A's weight is found in B. In this same scenario, the Jaccard score would be low because Message B has a lot of "extra" weight that message A lacks.



#### Similarity Score
The parameter `alpha` tries to balance the trade-off between exact structural matches and loose partial matches. It defines the weight distribution between Weighted Jaccard Similarity (which evaluates the overall overlap and penalizes extra or missing tokens) and Containment (which only cares if the first message's core "skeleton" exists within the second).

A high alpha (e.g., 0.9) treats the messages as a complete unit, making it ideal for finding near-identical logs where "extra junk" should lower the score. Conversely, a low alpha (e.g., 0.1) shifts the focus to the existence of the primary message within a larger context, allowing the matcher to ignore surrounding noise like timestamps, thread IDs, or stack trace fragments.

The overall similarity score is defined as
$$\text{similarity}=\alpha \cdot J + (1-\alpha) \cdot C$$

> A good recommendation for general log message is an $\alpha$ of 0.5!





## Data Handlers
The backend consists of two separate processes: Flask server and Docker scanner. Both run in parallel and need to access the same data. Data access is implemented via data collection handlers under `/data`. These handlers are shared objects between the two processes. The data is split into three concerns: *configurations*, *logs* and *records*.




### Configurations
Configuration data is essentially the settings that user can change via the *Settings* page in the UI. These settings are stored locally in a JSON file (`config.json`), to make them persistent. Users can export (and import) the configurations file from the application by using the file exchange in the *Settings* page. This makes it easy to migrate settings to other instances of other containers.

The handler `/data/config.py` provides many methods to load and store configuration data. The naming of the methods follows the hierarchial structure of the JSON file. This allows for the most flexibility, because an entire JSON property can be read with all its sub-properties.

**Example:** The method `scanner_tags_critical()` works on the the property `scanner.tags.critical`. The method `scanner_tags()` returns or overwrites the entire tags property `scanner.tags`. 
```
"scanner": {
    "interval": 5,
    "threshold": 0.85,
    "tags": {
        "critical": "[CRITICAL]",
        "error": "[ERROR]"
    }
}
```

All methods have optional arguments, meaning the same method is used for both reading and writing. If no argument is passed, the method simply reads its property from the file. If arguments are passed, the existing property gets overwritten with a new value.




### Logs
Every log item is defined based on the container that generated it, their timestamp and the category. Every log message produced by a Docker container, becomes a separate log item. Users can enable, which category of messages are actually logged and which ones are ignored.

The scanner clears all log items from the database at the start, so log item storage is not persistent. This does not really delete any data, just the parsed log items from this application. The log message strings are still available in the containers log! 

Log items are stored in a local SQL database file `logs.db`. This project uses [SQLAlchemy](https://docs.sqlalchemy.org/en/20/) as an abstraction layer for SQL queries. See the [Utilities](#utilities) section below for more details. It is not indented to share log data between containers.




### Records
Logs are messages of all types, while records usually are messages of critical failures or known errors. From a technical perspective, logs items and record items are the same, because they use same datatype. From a users perspective, log items are read-only, while record items can be edited. Users can change their timestamp, message text and even attache their own data.

This allows users to attache a markdown string as a *solution* or simple notes. Users can manually add a matching pattern to ensure reliable string matching and help with string similarity. A matching pattern is a regular expression (Regex) to identify a record based on its message string.




### Utilities
Datatypes used across the entire backend are implemented in the `utils.py` file.

The `DataItem` class is the mirror image of the implementation in the *React*/*JavaScript* frontend. It holds properties of data items (log items or record items) and provides useful methods for serialization.

The `DataItemEntity` class is used by the *SQLAlchemy* implementation and maps the properties of a data item to columns of the SQL database. It provides methods to parse data to/from database to useable data items.
